## D-1. Рукопожатие — ручная композиция вместо сертифицированной Noise-библиотеки

**Что сделано:** `crypto/noise/IkHandshake.kt` — рукопожатие по мотивам паттерна
Noise_IK, реализованное вручную поверх примитивов Bouncy Castle (X25519, HKDF/SHA-256,
Ed25519), а не поверх готовой реализации Noise Protocol Framework.

**Почему:** В песочнице, где собирался этот код, нет доступа к Maven Central/Google
Maven (сеть ограничена списком доменов без repo-хостов Android/Java-экосистемы), поэтому
я не мог фактически подключить и собрать проект с внешней Noise-библиотекой
(`noise-java`/`libnoiseforjava`/Snowy), чтобы подтвердить отсутствие конфликтов версий
Gradle/Kotlin/minSdk, как вы и просили. Компоновка вручную из библиотечных примитивов —
это НЕ создание нового алгоритма (см. PROJECT_SPEC.md 6.2): используются стандартные
DH/HKDF/AEAD/EdDSA из Bouncy Castle, схема — учебная композиция es/ee/se по спецификации
Noise.

**Риск:** ручная реализация протокола (даже из проверенных примитивов) не проходила
формальную верификацию/аудит, в отличие от `noise-java`. Основные вещи, которые я
постарался не упустить: аутентификация обеих сторон (подпись полного транскрипта
Ed25519), forward secrecy (эфемерные ключи на каждое соединение), защита от replay
(счётчик в AAD + строгое возрастание). Но самостоятельная реализация протокола — по
умолчанию кандидат на security review до продакшена.

**План закрытия:**
1. Локально (на машине с доступом к Maven Central) попробовать подключить `noise-java`
   (com.southernstorm:noise-java, если публикуется в подходящем репозитории) к модулю
   `crypto` и прогнать против него набор test vectors Noise_IK.
2. Если библиотека ставится без конфликтов версий и поддерживает нужный набор
   алгоритмов (25519 + ChaChaPoly + SHA256) — заменить `IkHandshake` на обёртку над ней,
   сохранив тот же внешний контракт (`startInitiator`/`startResponder`).
3. Если не ставится — заказать внешний security review именно `IkHandshake.kt` до
   выхода за пределы Stage 1 в продакшен (не блокирует внутреннее тестирование в LAN).

**Целевой этап:** не позднее Stage 4 (интернет-режим — там же, где повышаются ставки
из-за недоверенной сети).

**Обновление (Этап 2.5, D-4):** рукопожатие изменено — метка транскрипта `ramka-ik-v2`,
Message1/2/3 содержат зашифрованные поля (см. D-4 и раздел «ЭТАП 2.5» ниже). Это ещё
дальше от канонической Noise_IK: вместо симметричного состояния Noise (chaining key /
MixHash) используются отдельные HKDF-ключи `k1/k2/k3` с нулевым nonce, а подписи Ed25519
остаются поверх транскрипта. Объём security review `IkHandshake.kt` (пункт 3 плана
закрытия) соответственно вырос.

## D-2. Double Ratchet не реализован — сессионные ключи статичны в рамках соединения

**Что сделано:** Ключ сессии, полученный из IK-рукопожатия, используется для всех
сообщений в рамках ОДНОГО TCP-соединения (сейчас — одно сообщение на соединение, см.
D-3), но между независимыми рукопожатиями нет цепочки обновления ключей (KDF-цепочки
Double Ratchet), связывающей последовательные сессии друг с другом.

**Почему:** Double Ratchet — отдельная, самостоятельная по объёму часть протокола
(симметричный + DH-ratchet, управление skipped message keys), которую не успел
включить в объём этого MVP-прохода без риска внести ошибки без тестов.

**Риск:** нет forward secrecy МЕЖДУ разными сообщениями/сессиями сверх того, что даёт
свежий ECDH каждого рукопожатия (что само по себе уже даёт forward secrecy НА УРОВНЕ
соединения — компрометация одного сеансового ключа не раскрывает другие сеансы,
поскольку эфемерные ключи каждый раз новые). Отсутствует post-compromise security
(восстановление secrecy после временной компрометации долговременного ключа) в
классическом смысле Double Ratchet.

**План закрытия:** реализовать Double Ratchet (или Triple Ratchet) поверх текущего
`SessionCipher`, взяв HKDF-цепочку root key → chain key → message key, до начала
Stage 2 (там уже появляется очередь недоставленных сообщений и офлайн-доставка, где
разница между "IK каждый раз" и настоящим ratchet становится архитектурно значимой).

**Целевой этап:** Stage 2 (блокирует продолжение по вашему прямому указанию).

## D-3. Одно сообщение — одно TCP-соединение (рукопожатие на каждое сообщение)

**Что сделано:** `SecureLanChannel` проводит полное 3-сообщенческое IK-рукопожатие на
КАЖДОЕ отправляемое сообщение, затем закрывает соединение.

**Почему:** так проще и безопаснее для MVP — нет долгоживущего состояния сессии,
которое надо синхронизировать между переподключениями, реконнектами Wi-Fi и т.д.

**Риск:** только производительность/задержка (лишний round-trip и ECDH на каждое
сообщение) — на безопасность не влияет, каждое рукопожатие полноценно.

**План закрытия:** ввести переиспользуемые сессии с keep-alive и явным
пересогласованием по таймауту/ошибке, когда появится нагрузка на пропускную
способность (много сообщений подряд, вложения — Stage 6).

**Целевой этап:** не блокирует, можно закрыть в любой момент до Stage 6.

**Примечание (Этап 2.5):** для наблюдателя сети эта модель означает, что КАЖДОЕ сообщение
(включая ACK) выглядит как отдельное TCP-соединение из четырёх кадров (M1, M2, M3, данные).
Размеры кадров данных выровнены (см. 2.5-1), но сама структура «соединение на сообщение»
остаётся видимой. См. 2.5-4.

## D-4. Приватность статического ключа инициатора в рукопожатии — ЗАКРЫТО (Этап 2.5: D-4a + D-4b)

**Статус:** закрыто досрочно (планировалось на Stage 4). Закрытие согласовано владельцем
спецификации перед реализацией (схема утверждена целиком, правило 0.6).

**Что было:** `senderStaticX25519Pub` передавался в Message1 открытым текстом. Прежняя
оценка риска («не даёт содержательной информации») оказалась недостаточной: постоянный
ключ — стабильный идентификатор устройства, по которому наблюдатель сети может отслеживать
его между сетями и сменами IP, и это обесценивало выравнивание размеров из этапа 2.5.

**Что сделано:**
- **D-4a.** Message1 = `e_i_pub ‖ ChaCha20-Poly1305(k1, s_i_pub)`, 80 байт;
  `k1 = HKDF(es, salt = e_i_pub ‖ s_r_pub, info = "ramka-ik-v2-m1")`, `aad = e_i_pub ‖ s_r_pub`.
- **D-4b.** Подписи тоже зашифрованы: Message2 = `e_r_pub ‖ AEAD(k2, Sign_R)`, 112 байт;
  Message3 = `AEAD(k3, Sign_I)`, 80 байт; `k2/k3 = HKDF(es ‖ ee, salt = transcript,
  info = "ramka-ik-v2-m2" / "ramka-ik-v2-m3")`, `aad = transcript`.
  Причина: подпись поверх транскрипта проверяема публично (все входы транскрипта —
  открытые величины, `e_i` и `e_r` идут по проводу). Наблюдатель с публичными ключами-
  кандидатами (X25519 + Ed25519) мог бы подтвердить «A соединяется с B» без расшифровки.
  Без D-4b закрытие D-4a защищало бы только от сбора ключей «вслепую».
- Метка транскрипта сменена на `ramka-ik-v2` (старый и новый протоколы не принимают друг друга).
- Любая ошибка разбора/расшифровки (длина, low-order точка, тег, подпись) даёт `null` без
  различия причин; ответчик молча закрывает соединение без Message2.
- Публичный API `IkHandshake` не менялся, `SecureLanChannel` правок не потребовал.
- Тесты: `IkHandshakeTest` (подмена любого байта M1/M2/M3, replay M2/M3, reflection и
  отдельный тест разделения ключей, попытка «подтверждения по списку ключей» на настоящем
  транскрипте), `SecureLanChannelLoopbackTest` (размеры кадров на проводе, отсутствие `s_i`
  в записанном потоке, replay записанного соединения).

**Остаточные риски (принимаются осознанно):**
1. Компрометация статического ПРИВАТНОГО ключа ответчика позволяет расшифровать `s_i` в ранее
   записанном трафике (`k1` зависит только от `es`) — стандартное свойство IK. Подписи при
   этом остаются закрытыми: `k2/k3` зависят и от эфемерного `ee`.
2. Ответчик выполняет один X25519 и одну AEAD-проверку на каждое входящее соединение ДО
   аутентификации. Для LAN стоимость мала; ограничивается таймаутами сокета (см. 2.5-5).
3. Записанный Message1 можно воспроизвести: он проходит расшифровку, ответчик отвечает
   Message2, но Message3 не сходится (другая эфемерная пара) — сообщение не доставляется,
   состояние не накапливается (проверено тестом replay).
4. Нулевой nonce AEAD безопасен ТОЛЬКО пока `k1/k2/k3` одноразовые (выведены из свежих
   эфемерных ключей, разные `info`). Любое будущее повторное использование этих ключей —
   нарушение инварианта и требует пересмотра схемы.
5. Не скрыты: факт соединения, IP:IP и время, размеры/структура рукопожатия, фиксированный
   порт, тип mDNS-сервиса — см. 2.5-4.

**Целевой этап:** закрыто в Этапе 2.5.

## D-5. Replay-защита — только строгое возрастание счётчика в рамках сессии

**Что сделано:** `SessionCipher` отклоняет входящий пакет с номером ≤ последнего
принятого (см. crypto/ratchet/SessionCipher.kt), без скользящего окна для приёма не по
порядку пришедших пакетов.

**Почему:** оправдано для TCP (гарантированная доставка по порядку внутри одного
соединения) и для дизайна "одно сообщение — одно соединение" (D-3): в этой модели
всегда ровно один пакет с counter=0, окно не нужно.

**Риск:** появится при переходе на модель с несколькими сообщениями на сессию/на
ненадёжный транспорт (UDP, relay с возможной пересортировкой) — там нужно окно с
битовой маской, иначе легитимные, но переупорядоченные пакеты будут отбрасываться.

**План закрытия:** добавить скользящее окно (как в WireGuard/IPsec) при снятии
ограничения D-3.

**Целевой этап:** синхронно с D-3.

## D-6. Счётчики SessionCipher — в памяти, без персистентности (условие на будущее)

**Что сделано:** `SessionCipher.sendCounter`/`lastAcceptedRecvCounter` — обычные `var`
в памяти объекта, ничего не сохраняется на диск. Отдельного класса `CounterStorage`
в проекте нет.

**Почему это допустимо сейчас:** инвариант, на котором это держится — **сессионные
ключи уникальны для каждого соединения** (свежий эфемерный ECDH в каждом IK-рукопожатии,
см. D-3). `SessionCipher` живёт ровно на время одного TCP-соединения и вызывает
`wipe()` по завершении. Раз ключ никогда не переживает соединение, счётчику,
завязанному на этот ключ, тоже нечего переживать — nonce с одним и тем же ключом
физически не может повториться между разными объектами `SessionCipher`, потому что
у каждого свой ключ.

**ОБЯЗАТЕЛЬНОЕ УСЛОВИЕ (блокирует, если нарушается молча):** это рассуждение
перестаёт быть верным в момент, когда D-3 снимается — то есть когда появляется
сессия на несколько сообщений, resumption рукопожатия или кэширование/переиспользование
сессионных ключей между соединениями. В любом из этих случаев ключ начинает
переживать создание объекта, который его держит, и тогда счётчик ОБЯЗАН
переживать вместе с ним — иначе перезапуск процесса или пересоздание объекта в
памяти обнулит счётчик под тем же ключом и откроет повторное использование nonce.
**`CounterStorage` с персистентным хранением последнего использованного номера на
ключ (или на контакт) должен быть реализован ДО, а не после соответствующего
изменения** — снятие D-3 без одновременной реализации `CounterStorage` не
принимается как промежуточное состояние, даже временное.

**Целевой этап:** синхронно с D-3/D-5, как обязательное предусловие, не отдельная
задача "потом".

## D-V. Верификация ключа — модальный диалог вместо отдельного экрана

**Что сделано:** Экран верификации ключа из §8.4 реализован как `KeyVerificationDialog`
— модальный `AlertDialog`, показывается поверх `QrScreen` сразу после успешного
распознавания QR, а не как отдельный маршрут в `RamkaNavHost` со своим `Route`.

**Почему:** для MVP это функционально эквивалентно — пользователь видит отпечаток,
сверяет его с собеседником, подтверждает или отменяет добавление, прежде чем
контакт попадёт в базу. Разница только в навигационном механизме (диалог поверх
текущего экрана vs отдельный push в back stack), не в содержании проверки или в
том, что можно случайно пропустить шаг верификации.

**Риск:** минимальный, в основном UX — диалог нельзя, например, открыть по
глубокой ссылке или вернуться к нему из истории навигации отдельно от экрана QR.
На безопасность самой процедуры верификации (что показывается, что сравнивается,
что происходит при несовпадении) это не влияет — эти решения не зависят от того,
диалог это или экран.

**План закрытия:** если отдельный маршрут в навигации всё же нужен (например, для
глубоких ссылок или для будущего сценария "показать верификацию позже, не сразу
после скана") — вынести `KeyVerificationDialog` в полноценный composable-экран с
собственным route в `RamkaNavHost`, передавая `Invite` через `SavedStateHandle`
или временное хранилище во `QrViewModel`.

**Целевой этап:** не блокирует Stage 1; делать по запросу, не проактивно.

## ЭТАП B — решения по Outbox / ACK (задачи 1, 5, 6)

Не отклонения от спеки, а фиксация архитектурных решений там, где спецификация
не даёт однозначного механизма (директива v2, правило 0: "не описано — спросить,
не додумывать" — здесь додумано, но задокументировано, а не спрятано).

- **D-3/D-6 подтверждаю НЕ снятыми.** `ProcessOutboxUseCase`/`SendMessageUseCase`
  оба идут через единственную точку — `AttemptDeliveryUseCase` →
  `TransportRepository.sendEncryptedPacket` → `SecureLanChannel`, которая как и
  раньше делает полное 3-сообщенческое IK-рукопожатие на КАЖДУЮ попытку, без
  переиспользования сессии/ключа между попытками. `CounterStorage`
  по-прежнему не создавался и не нужен.
- **Семантика "SENT" vs "DELIVERED" разделена.** Удачная отправка по сокету
  (рукопожатие+TCP прошли) даёт статус `SENT` и снимает запись из Outbox — ПОВТОРНАЯ
  отправка самого текста больше не делается. Статус `DELIVERED` выставляется
  отдельно, только по факту получения DELIVERED-ACK от собеседника. Если бы Outbox
  держал запись до получения ACK, потеря самого ACK (не текста) заставляла бы
  бесконечно пересылать уже доставленный текст-дубликат — сочтено худшим
  поведением, чем риск того, что статус навсегда останется на `SENT`, если ACK
  потеряется.
- **DELIVERED-ACK/READ-ACK — best-effort, НЕ через Outbox.** Если ACK не дошёл,
  повторной попытки ИМЕННО ACK нет — статус сообщения у отправителя просто
  останется на предыдущей ступени (`SENT` вместо `DELIVERED`, либо `DELIVERED`
  вместо `READ`). Это осознанно принятая деградация, а не забытый кейс: заводить
  вторую независимую очередь ретраев для служебных ACK ради строгой доставки
  каждого — сочтено несоразмерным объёму этапа B. Статус при этом никогда не лжёт
  в опасную сторону (не показывает "прочитано", если фактически не прочитано) —
  ухудшение только в сторону "показывает менее продвинутый статус, чем есть на
  самом деле", что безопасно.
- **ID сообщения в конверте — обязательное добавление, не в исходном тексте
  задачи.** У отправителя и получателя разные `localId` для одного и того же
  сообщения (глобального ID нет, п. 3.1). Без поля `messageId` в
  `AppMessage.Text` ACK был бы физически нечем сопоставлять с исходной записью —
  добавлено поле `Message.remoteMessageId` (только для входящих) и `messageId`
  в конверте (см. `AppMessage.kt`). Это необходимое дополнение к тому, что было
  прямо описано в задаче 5, а не самостоятельное расширение объёма.
- **Статусы движутся только вперёд.** `IncomingMessageProcessor.advanceStatus`
  игнорирует ACK, который откатил бы статус назад (например, задержавшийся
  DELIVERED-ACK, пришедший после того, как уже применился READ-ACK) —
  простая защита от переупорядочивания на сети, не требует счётчиков/окон.

- **Flush очереди: ОДНО соединение и одно полное рукопожатие НА ОДНО сообщение
  (ревью п.3, D-3/D-6).** При N недоставленных сообщениях одному контакту
  `ProcessOutboxUseCase` в цикле делает N независимых вызовов `attemptDelivery` →
  `SecureLanChannel.sendMessage`; каждый открывает новый сокет, проходит полное
  3-сообщенческое IK-рукопожатие с нуля (свежие эфемерные ключи, `SessionCipher` со
  счётчиком с 0), отправляет РОВНО ОДИН зашифрованный кадр и закрывается. Батч-пересылка
  (одно соединение с N кадрами) НЕ реализована и не реализуется без предварительного
  персистентного `CounterStorage` (D-6). Выбор осознанный, не упущение: цена —
  N рукопожатий вместо одного (производительность, D-3), безопасность не затронута.
- **Батч допустим только для READ-ACK (ревью п.4).** `AppMessage.ReadAck` несёт список
  ID; при открытии чата уходит ОДИН ReadAck на все неподтверждённые входящие — это
  одно соединение = одно рукопожатие = одно сообщение (сам ReadAck), то есть
  D-3 не нарушается: батчится содержимое одного кадра, а не число кадров в сессии.
  Только для сообщений в статусе DELIVERED и выше (у входящих это истинно по
  построению; фильтр оставлен явным). `DeliveredAck` батч НЕ поддерживает.
- **Идемпотентный приём (ревью п.2).** `HandleIncomingTextUseCase`: дубликат по
  `(contactId, remoteMessageId)` не создаёт вторую запись и не вызывает уведомление,
  но DELIVERED-ACK уходит повторно (у отправителя мог потеряться ACK). Проверено
  pure-JVM тестом `HandleIncomingTextUseCaseTest`.
- **Формат ACK (ревью п.2).** Только тег типа + ID(ы) сообщения отправителя
  (UUIDv4, ровно 36 ASCII-байт каждый; декодер отвергает любую иную длину). Ни
  временных меток, ни ID контактов, ни содержимого.
- **POST_NOTIFICATIONS (ревью п.5).** Запрашивается автоматически ОДИН раз при первом
  показе списка контактов (API 33+), дальше — только по кнопке «Повторить»/«Открыть
  настройки» (паттерн CAMERA). Флаг «уже спрашивали» — в обычном `SharedPreferences`
  (`AppPreferences`), а не в `SecureKeyStore`: это не секрет, а контракт
  `KeyValueStore` писан для ключевого материала. Уведомление: title «ramka»,
  text «Новое сообщение», `publicVersion` идентична, без extras/ticker.
- **Миграция БД v1→v2** — явная `Migration` (таблица `outbox` + колонки
  `messages.remoteMessageId`, `messages.readAckSent`), без destructive-фолбэка:
  существующие контакты и переписка сохраняются.

- **ЭТАП B.8 — тип foreground-сервиса: `specialUse`.** Выбор и причины:
  - `dataSync` отвергнут: на Android 15 (при `targetSdk` 35) система даёт таким сервисам
    6 часов из 24, затем вызывает `onTimeout` и требует остановить сервис — иначе
    `RemoteServiceException`. Для сервиса «держать процесс живым» это неприемлемо.
    Сейчас `targetSdk` = 34, лимит ещё не действует, но сработает при повышении target.
  - `connectedDevice` отвергнут: тип описан для внешних устройств (Bluetooth/NFC/IR/USB и
    т.п.), а не для приёма по локальной сети; использовать его ради обхода лимита —
    неправдивое объявление типа.
  - `specialUse`: без лимита по времени; требует разрешение
    `FOREGROUND_SERVICE_SPECIAL_USE` и обоснование в манифесте
    (`PROPERTY_SPECIAL_USE_FGS_SUBTYPE`) — оба добавлены, обоснование написано в `<service>`.
    Распространение только через GitHub, поэтому Play-декларация не нужна.
  - **Новое разрешение в манифесте** (`FOREGROUND_SERVICE_SPECIAL_USE`, обычное, без
    runtime-диалога). Это не зависимость, но фиксирую отдельно, как и остальные разрешения.
- **Сервис стартует только с экрана.** Старт foreground-сервиса из фона на Android 12+
  запрещён, а `RamkaApp.onCreate` может выполняться в процессе, поднятом WorkManager'ом.
  Поэтому `applyScheduling()` (безопасно везде) вызывается из `RamkaApp`, а
  `applyService()` — из `MainActivity.onStart` и из настроек. `RECEIVE_BOOT_COMPLETED`
  НЕ добавлялся (новое разрешение без одобрения): после перезагрузки телефона сервис
  вернётся, когда пользователь откроет приложение. Перезапуск сервиса самой системой
  после убийства (`START_STICKY`) на реальных устройствах НЕ проверялся.
- **Сервис ничего не хранит (B.8.4).** У `PersistentDeliveryService` нет полей, зависимостей,
  доступа к БД, outbox или ключам; он только показывает уведомление и держит процесс.
  Приёмник входящих и mDNS живут в Application-scope, как и раньше. Отдельного кэша ключей
  нет, контракт `KeyValueStore` не затронут.
- **Главный тумблер управляет только WorkManager.** Приёмник и mDNS-обнаружение внутри
  живого процесса продолжают работать независимо от него (как и до задачи 8) — тумблер
  выключает именно периодический sweep и (каскадом) сервис.
- **Когда показывается OEM-подсказка.** Главный тумблер по умолчанию ВКЛ, поэтому
  «первое включение» на практике = первое открытие настроек с включённой фоновой доставкой
  (либо включение тумблера, если подсказка ещё не показывалась). Не на старте приложения —
  чтобы не наслаиваться на системный запрос `POST_NOTIFICATIONS`. Недостаток: кто никогда
  не откроет настройки, подсказку не увидит — компенсируется README. Флаг «показано» —
  обычный `SharedPreferences`; ручное повторное открытие флаг не сбрасывает и не трогает.
- **Отнесение производителей к семействам — допущение.** Xiaomi = Xiaomi/Redmi/POCO/Black Shark;
  Huawei = Huawei/Honor; OPPO = OPPO/realme/OnePlus; vivo = vivo/iQOO. Названия пунктов меню
  меняются от версии прошивки к версии, тексты подсказок — ориентир, а не гарантия.
- **Добавлен вход в настройки (⚙ в шапке списка контактов).** До этого `onOpenSettings`
  нигде не вызывался и экран настроек был недостижим; без этого тумблеры задачи 8 нельзя
  было бы открыть. На экран чата это не влияет.
- **Каналы уведомлений.** Оба канала — `IMPORTANCE_DEFAULT` (не LOW: на части OEM-прошивок
  LOW молча не показывается). Канал сервиса дополнительно без звука и вибрации.

- **WorkManager зафиксирован на 2.9.1, не на последней стабильной.** Начиная с 2.10.0
  сам WorkManager собирается под `compileSdk 35`, и по правилам AAR-метаданных это
  требование переходит на потребителя — сборка падает с "requires compileSdk 35 or
  later" уже на `:app:checkDebugAarMetadata`, хотя весь проект (все модули, AGP 8.5.2)
  сидит на `compileSdk 34`. Сначала (см. более ранний диалог) была подключена 2.11.2 —
  моя ошибка, версию не сверил с текущим compileSdk проекта. 2.9.1 — последний
  стабильный патч в линейке, ещё собранной под SDK 34; API, которые используются
  (`CoroutineWorker`, `PeriodicWorkRequestBuilder`, `Constraints`,
  `enqueueUniquePeriodicWork`, `cancelUniqueWork`), в нём присутствуют без изменений.
  **Если понадобится 2.10+ — сначала поднимать `compileSdk`/`targetSdk` до 35 и AGP
  до 8.6.0+ по всему проекту осознанно и отдельным изменением, не тихо вместе с
  обновлением одной библиотеки.**

- **Вибрация по умолчанию для канала сообщений.** `enableVibration(true)` +
  `vibrationPattern` на канале и `.setVibrate()` на самом уведомлении. Важность
  канала осталась `IMPORTANCE_DEFAULT` (уже была верна). Важный для тестирования
  нюанс: `NotificationChannel`, однажды созданный на устройстве, Android больше не
  даёт менять программно — если приложение уже стояло с прежней версией канала
  (без вибрации), новые настройки применятся только на чистой установке или после
  ручного удаления канала в системных настройках.
- **Счётчик непрочитанных (badge) — не в исходной спеке, UX-добавление по прямому
  запросу.** `Contact.unreadCount`, миграция БД v2→v3 (`ALTER TABLE contacts ADD
  COLUMN unreadCount INTEGER NOT NULL DEFAULT 0`, без потери данных). Инкремент —
  в `HandleIncomingTextUseCase`, только на реально новое (не дублирующее) сообщение,
  покрыто тестами. Сброс — в `ChatViewModel` при открытии чата, независимо от
  READ-ACK (badge про факт прочтения пользователем, ACK — про подтверждение
  отправителю; это разные вещи, которые могут разойтись, если ACK не дошёл).
  Сортировка "непрочитанные вверху" сделана на уровне SQL-запроса
  (`ORDER BY (unreadCount > 0) DESC, alias`), а не в Kotlin-коде.
- **Поле ввода поверх навигационной панели — исправлен реальный баг, не UX-догадка.**
  `Scaffold.bottomBar` в Compose НЕ получает автоматических insets (в отличие от
  content-слота) — это и была причина. Добавлены `navigationBarsPadding()` +
  `imePadding()` на контейнер `MessageInputBar`. Задача 9 (UI чата не менять) этим
  не нарушена — макет/цвета/пузыри не тронуты, это точечный фикс отступа тем же
  элементом, что и раньше.

- **Счётчик непрочитанных и открытый чат (исправление).** Первая версия сбрасывала
  счётчик только в момент открытия чата, поэтому сообщение, пришедшее в уже открытый чат,
  всё равно увеличивало badge (он появлялся после выхода из чата за уже увиденное).
  Добавлен `ActiveChatTracker` (только id контакта в памяти): `ChatScreen` по lifecycle
  (ON_START/ON_STOP) сообщает, что чат виден; `HandleIncomingTextUseCase` не увеличивает
  счётчик, пока чат этого контакта виден. Свёрнутое приложение с открытым чатом
  считается «чат скрыт», сообщения в нём идут в непрочитанные. Сообщение при этом
  сохраняется и подтверждается DELIVERED-ACK как обычно; READ-ACK за сообщения,
  пришедшие пока чат уже открыт, уходит при следующем показе чата (не мгновенно).
  Дополнительно счётчик обнуляется и при выходе из чата (страховка от гонки при открытии):
  всё, что пришло, пока экран был виден, пользователь уже видел. Симптом, с которого
  началось исправление: после выхода из чата бейдж и жирный шрифт оставались.

## ЭТАП 2.5 — защита от анализа трафика (статус: в работе)

Требований в `PROJECT_SPEC.md` для этого этапа нет (файла нет), поэтому рамки этапа
согласованы в переписке: выравнивание размеров, сглаживание временных паттернов, отсутствие
постоянных идентификаторов и сигнатур на проводе, честная модель угроз.

### 2.5-1. Выравнивание размера тела (`crypto/padding/FramePadding`)

Перед шифрованием тело `AppMessage` оборачивается в `[флаги 1 Б][длина 4 Б][payload][нули]`
и округляется до корзин 128 / 256 / 512 / 1024 / 2048 / 4096 байт, выше — кратно 4096
(максимум 8 МБ − 4096). Выравнивание целиком внутри AEAD. Подключено в
`SecureLanChannel` (`pad` перед шифрованием, `unpad` после расшифровки). Формат каноничен:
`unpad` отвергает неверный размер, ненулевой хвост, неизвестные флаги. Тело с флагом
`FLAG_COVER` (резерв под фиктивные пакеты) молча отбрасывается. `AppMessage`, `Message`,
`Contact`, БД и Outbox не затронуты (в Outbox по-прежнему лежит исходное тело).

Эффект: DELIVERED-ACK, READ-ACK с несколькими ID и текст до ~86 байт дают одинаковую длину
кадра данных (корзина 128: длина кадра 153, с байтом типа и счётчиком).

**Риск/ограничение:** длина выровненного тела — всё ещё функция размера сообщения с
точностью до корзины; длинные сообщения различимы по корзине. Тело больше 8 МБ не
отправляется (`sendMessage` возвращает `false` до соединения).

### 2.5-2. Разрыв совместимости формата провода

Изменения 2.5-1 и D-4 несовместимы со старыми версиями. Решение владельца: оба устройства
обновляются одновременно, обратная совместимость не поддерживается. Пока версии разные,
сообщения не теряются: приёмник отбрасывает незнакомый формат, а отправитель оставляет
сообщение в Outbox и повторяет доставку после обновления второго устройства.

### 2.5-3. Правки крипто-ядра по правилу 0.6 (`IkHandshake.kt`)

Все изменения согласованы схемой перед реализацией (см. D-4). Дополнительно, мелкие:
- `computeTranscript` стал `internal` (был `private`) — чтобы тест воспроизводил атаку
  наблюдателя с настоящим транскриптом; поведение не менялось.
- `startInitiator` теперь выполняет DH при создании Message1: некорректный (low-order)
  статический ключ контакта вызывает `IllegalStateException` сразу, а не в `consumeMessage2`.
  Для вызывающего кода (`sendMessage`) это та же неудачная попытка (`false`).
- Low-order эфемерные точки в Message1/Message2 дают `null`, а не исключение.

### 2.5-4. Что остаётся видимым наблюдателю LAN после этапа

- Факт соединения, IP-адреса, время (D-3: одно сообщение — одно соединение, ACK тоже).
- Структура соединения: четыре кадра фиксированных размеров (81 / 113 / 81 в поле длины для
  M1/M2/M3, затем кадр данных = размер корзины + 25), плюс кадр данных одной из корзин.
- Открытые байты типа кадра (1–4) и поле длины — пока не снято (запланировано, 2.5-5).
- Фиксированный TCP-порт и тип mDNS-сервиса `_ramka._tcp.` (случайно только имя
  экземпляра): приложение обнаруживается без анализа TCP. Порт записан в QR-приглашении, а
  `lastKnownAddress` не обновляется, поэтому смена порта вне рамок этапа.
- Тайминги: DELIVERED-ACK уходит сразу после приёма, READ-ACK — при открытии чата,
  повторы Outbox идут по детерминированному backoff (30 с × 2ⁿ, потолок 1 ч). Джиттер ещё
  не добавлен (2.5-5).
- Relay-транспорта в кодовой базе нет (только тип `NetworkAddress.Relay` и колонка БД), этап
  касается только LAN. Для relay padding переиспользуется, но у relay будет свой наблюдатель.

### 2.5-5. Ещё не сделано (по согласованному порядку)

1. Фиксированные кадры рукопожатия без байта типа и поля длины (роль определяется позицией);
   у кадра данных — длина только из набора корзин.
2. Джиттер: случайная задержка DELIVERED-ACK/READ-ACK (константы в одном конфиге, по
   умолчанию включено; READ-ACK помечается отправленным ДО отложенной отправки, чтобы не
   было дублей) и ±20% на backoff Outbox.
3. `soTimeout` на входящих соединениях (молчащее соединение сейчас висит бесконечно).
4. Тумблер mDNS-обнаружения в настройках (по умолчанию включено).
5. Фиктивный трафик — опционально, выключен по умолчанию, только если оценка эффекта оправдает цену.

## D-7. `androidx.security:security-crypto` — вся библиотека deprecated с 1.1.0, замены нет

**Что сделано:** `SecureKeyStore.kt` продолжает использовать `MasterKey` и
`EncryptedSharedPreferences` из `androidx.security:security-crypto:1.1.0` с явным
`@file:Suppress("DEPRECATION")` на уровне файла.

**Почему:** начиная с версии 1.1.0 Google пометил **весь** пакет
`security-crypto` как deprecated (`MasterKey`, `EncryptedSharedPreferences` и оба
вложенных enum'а `PrefKeyEncryptionScheme`/`PrefValueEncryptionScheme` — целиком,
не один метод). Библиотека при этом функционально не удалена и не сломана —
Google не предоставил официальной замены на момент этой правки. Судя по всему,
именно отсюда — большая часть из 11 warnings `:crypto:compileDebugKotlin`,
которые видны на скриншотах сборки (сам список текстом мне не передавался — см.
README, раздел про известные warnings).

Отдельно стоит сказать честно: именно я в одном из предыдущих проходов поднял
версию с `1.1.0-alpha06` на стабильный `1.1.0`, думая, что это чистое улучшение
(стабильный релиз вместо альфы) — на деле это и включило пакет deprecated-warnings,
которых на alpha06 не было. Пометка "весь пакет deprecated" на связку
MasterKey+EncryptedSharedPreferences появилась именно в 1.1.0.

**Риск:** чисто гигиенический/репутационный (шумные warnings в логе сборки,
потенциальные проблемы при будущем удалении API из более новых версий
Android Gradle Plugin/Kotlin, которые могут повысить уровень некоторых
deprecation-warnings до ошибок). Функционального риска для безопасности нет —
класс работает точно так же, как и раньше, реализация не изменилась.

**План закрытия:** дождаться официальной замены от Google (на момент правки её
нет) или перейти на самостоятельную реализацию поверх `android.security.keystore`
напрямую (`KeyGenParameterSpec` + `Cipher` с AES/GCM, без обёртки
EncryptedSharedPreferences) — но это уже реальное изменение крипто-соседнего кода,
требует отдельного согласования по правилу 0.6/0.3, не делать проактивно.

**Целевой этап:** не блокирует Stage 1/2; пересмотреть при первом столкновении с
реальной несовместимостью (например, если Google полностью уберёт классы в
будущей мажорной версии) или по вашему явному запросу.

## Закрыто в этом проходе (для истории)

- D-4 (открытый статический ключ инициатора в Message1) — закрыто в Этапе 2.5 вместе с
  шифрованием подписей в Message2/Message3 (D-4a + D-4b), см. D-4 выше.
- Подпись полного транскрипта рукопожатия Ed25519 обеими сторонами — реализовано
  (`IkHandshake.InitiatorSession`/`ResponderSession`, поле `Sign_I`/`Sign_R`).
- Вывод ключа сессии из эфемерного ECDH на каждое соединение (es/ee/se) — реализовано.
- Nonce на основе счётчика сообщений, начинается с нуля на соединение, не
  переиспользуется в рамках одного ключа — реализовано (`MessageCipher.nonceFor`).
- Номер сообщения в AAD, дубликаты отбрасываются — реализовано (`SessionCipher`).
- mDNS instance name — случайный, генерируется заново при каждом запуске приложения,
  не содержит имени устройства/пользователя — реализовано (`RamkaApp.onCreate`).
- Пароль SQLCipher — случайные 32 байта, хранится в `SecureKeyStore`
  (EncryptedSharedPreferences поверх Android Keystore), не в открытом виде на диске и
  нигде не логируется.
