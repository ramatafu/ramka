# DEVIATIONS.md — реестр отклонений от PROJECT_SPEC.md

Каждое отклонение: что сделано вместо канонического решения, почему, риск, план закрытия, целевой этап. Правило: ничего из этого списка не переносится молча в Stage 2 — пункты со статусом «блокирует» должны быть закрыты или осознанно переутверждены владельцем спецификации до начала следующего этапа.

## D-1. Рукопожатие — ручная композиция вместо сертифицированной Noise-библиотеки
**Что сделано:** `crypto/noise/IkHandshake.kt` — рукопожатие по мотивам паттерна Noise_IK, реализованное вручную поверх примитивов Bouncy Castle (X25519, HKDF/SHA-256, Ed25519), а не поверх готовой реализации Noise Protocol Framework.

**Почему:** В песочнице, где собирался этот код, нет доступа к Maven Central/Google Maven (сеть ограничена списком доменов без repo-хостов Android/Java-экосистемы), поэтому я не мог фактически подключить и собрать проект с внешней Noise-библиотекой, чтобы подтвердить отсутствие конфликтов версий. Компоновка вручную из библиотечных примитивов — это НЕ создание нового алгоритма: используются стандартные DH/HKDF/AEAD/EdDSA из Bouncy Castle, схема — учебная композиция es/ee/se по спецификации Noise.

**Риск:** ручная реализация протокола не проходила формальную верификацию/аудит. Основные вещи учтены: аутентификация обеих сторон, forward secrecy, защита от replay. Но самостоятельная реализация протокола — по умолчанию кандидат на security review до продакшена.

**План закрытия:**
1. Локально попробовать подключить noise-java к модулю crypto и прогнать test vectors Noise_IK.
2. Если библиотека ставится без конфликтов — заменить `IkHandshake` на обёртку над ней.
3. Если не ставится — заказать внешний security review именно `IkHandshake.kt` до выхода за пределы Stage 1 в продакшен.

**Целевой этап:** не позднее Stage 4.

**Обновление (Этап 2.5, D-4):** рукопожатие изменено — метка транскрипта `ramka-ik-v2`, Message1/2/3 содержат зашифрованные поля. Это ещё дальше от канонической Noise_IK: вместо симметричного состояния Noise используются отдельные HKDF-ключи k1/k2/k3 с нулевым nonce, а подписи Ed25519 остаются поверх транскрипта. Объём security review `IkHandshake.kt` соответственно вырос.

## D-2. Double Ratchet не реализован — сессионные ключи статичны в рамках соединения
**Что сделано:** Ключ сессии, полученный из IK-рукопожатия, используется для всех сообщений в рамках ОДНОГО TCP-соединения, но между независимыми рукопожатиями нет цепочки обновления ключей.

**Почему:** Double Ratchet — отдельная, самостоятельная по объёму часть протокола, которую не успел включить в объём этого MVP-прохода без риска внести ошибки без тестов.

**Риск:** нет post-compromise security (восстановление secrecy после временной компрометации долговременного ключа) в классическом смысле Double Ratchet. Но forward secrecy на уровне соединения есть (свежий ECDH каждый раз).

**План закрытия:** реализовать Double Ratchet (или Triple Ratchet) поверх текущего `SessionCipher`, взяв HKDF-цепочку root key → chain key → message key, до начала Stage 2.

**Целевой этап:** Stage 2 (блокирует продолжение по прямому указанию).

## D-3. Одно сообщение — одно TCP-соединение (рукопожатие на каждое сообщение)
**Что сделано:** `SecureLanChannel` проводит полное 3-сообщенческое IK-рукопожатие на КАЖДОЕ отправляемое сообщение, затем закрывает соединение.

**Почему:** так проще и безопаснее для MVP — нет долгоживущего состояния сессии, которое надо синхронизировать между переподключениями.

**Риск:** только производительность/задержка (лишний round-trip и ECDH на каждое сообщение) — на безопасность не влияет, каждое рукопожатие полноценно.

**План закрытия:** ввести переиспользуемые сессии с keep-alive и явным пересогласованием по таймауту/ошибке, когда появится нагрузка на пропускную способность (Stage 6).

**Целевой этап:** не блокирует, можно закрыть в любой момент до Stage 6.

**Примечание (Этап 2.5):** для наблюдателя сети эта модель означает, что КАЖДОЕ сообщение (включая ACK) выглядит как отдельное TCP-соединение из четырёх кадров (M1, M2, M3, данные). Размеры кадров данных выровнены (см. 2.5-1), но сама структура «соединение на сообщение» остаётся видимой. См. 2.5-4.

## D-4. Приватность статического ключа инициатора в рукопожатии — ЗАКРЫТО (Этап 2.5: D-4a + D-4b)
**Статус:** закрыто досрочно (планировалось на Stage 4). Закрытие согласовано владельцем спецификации перед реализацией (схема утверждена целиком, правило 0.6).

**Что было:** `senderStaticX25519Pub` передавался в Message1 открытым текстом. Прежняя оценка риска оказалась недостаточной: постоянный ключ — стабильный идентификатор устройства, по которому наблюдатель сети может отслеживать его между сетями и сменами IP.

**Что сделано:**
- **D-4a.** Message1 = `e_i_pub ‖ ChaCha20-Poly1305(k1, s_i_pub)`, 80 байт; `k1 = HKDF(es, salt = e_i_pub ‖ s_r_pub, info = "ramka-ik-v2-m1")`, `aad = e_i_pub ‖ s_r_pub`.
- **D-4b.** Подписи тоже зашифрованы: Message2 = `e_r_pub ‖ AEAD(k2, Sign_R)`, 112 байт; Message3 = `AEAD(k3, Sign_I)`, 80 байт; `k2/k3 = HKDF(es ‖ ee, salt = transcript, info = "ramka-ik-v2-m2" / "ramka-ik-v2-m3")`, `aad = transcript`.
- Метка транскрипта сменена на `ramka-ik-v2` (старый и новый протоколы не принимают друг друга).
- Любая ошибка разбора/расшифровки даёт `null` без различия причин; ответчик молча закрывает соединение без Message2.
- Публичный API `IkHandshake` не менялся, `SecureLanChannel` правок не потребовал.
- Тесты: `IkHandshakeTest` (подмена любого байта M1/M2/M3, replay, reflection, попытка «подтверждения по списку ключей»), `SecureLanChannelLoopbackTest` (размеры кадров на проводе, отсутствие `s_i` в записанном потоке).

**Остаточные риски (принимаются осознанно):**
1. Компрометация статического ПРИВАТНОГО ключа ответчика позволяет расшифровать `s_i` в ранее записанном трафике (`k1` зависит только от `es`) — стандартное свойство IK.
2. Ответчик выполняет один X25519 и одну AEAD-проверку на каждое входящее соединение ДО аутентификации. Для LAN стоимость мала; ограничивается таймаутами сокета (см. 2.5-5).
3. Записанный Message1 можно воспроизвести: он проходит расшифровку, ответчик отвечает Message2, но Message3 не сходится — сообщение не доставляется.
4. Нулевой nonce AEAD безопасен ТОЛЬКО пока `k1/k2/k3` одноразовые.
5. Не скрыты: факт соединения, IP:IP и время, размеры/структура рукопожатия, фиксированный порт, тип mDNS-сервиса — см. 2.5-4.

**Целевой этап:** закрыто в Этапе 2.5.

## D-5. Replay-защита — только строгое возрастание счётчика в рамках сессии
**Что сделано:** `SessionCipher` отклоняет входящий пакет с номером ≤ последнего принятого, без скользящего окна.

**Почему:** оправдано для TCP и для дизайна "одно сообщение — одно соединение" (D-3): в этой модели всегда ровно один пакет с counter=0, окно не нужно.

**Риск:** появится при переходе на модель с несколькими сообщениями на сессию/на ненадёжный транспорт — там нужно окно с битовой маской.

**План закрытия:** добавить скользящее окно при снятии ограничения D-3.

**Целевой этап:** синхронно с D-3.

---

## D-6. Счётчики SessionCipher — в памяти, без персистентности
**Что сделано:** Счётчики nonce хранятся только в памяти объекта `SessionCipher`, который живёт ровно на время одного TCP-соединения.

**Почему это допустимо сейчас:** инвариант — сессионные ключи уникальны для каждого соединения (свежий эфемерный ECDH в каждом IK-рукопожатии, см. D-3). Раз ключ никогда не переживает соединение, счётчику тоже нечего переживать.

**ОБЯЗАТЕЛЬНОЕ УСЛОВИЕ:** это рассуждение перестаёт быть верным в момент, когда D-3 снимается. В любом из этих случаев ключ начинает переживать создание объекта, и тогда счётчик ОБЯЗАН переживать вместе с ним. `CounterStorage` с персистентным хранением должен быть реализован ДО, а не после соответствующего изменения.

**Целевой этап:** синхронно с D-3/D-5, как обязательное предусловие.

## ЭТАП B — решения по Outbox / ACK (задачи 1, 5, 6)

Не отклонения от спеки, а фиксация архитектурных решений там, где спецификация не даёт однозначного механизма.

- **D-3/D-6 подтверждаю НЕ снятыми.** `ProcessOutboxUseCase`/`SendMessageUseCase` оба идут через `AttemptDeliveryUseCase` → `TransportRepository.sendEncryptedPacket` → `SecureLanChannel`, которая делает полное 3-сообщенческое IK-рукопожатие на КАЖДУЮ попытку.
- **Семантика "SENT" vs "DELIVERED" разделена.** Удачная отправка по сокету даёт статус `SENT` и снимает запись из Outbox. Статус `DELIVERED` выставляется отдельно, только по факту получения DELIVERED-ACK.
- **DELIVERED-ACK/READ-ACK — best-effort, НЕ через Outbox.** Если ACK не дошёл, повторной попытки ИМЕННО ACK нет. Статус при этом никогда не лжёт в опасную сторону. **Известное ограничение (Этап 2.5):** если процесс убит во время задержки джиттера (до 5 с), DELIVERED-ACK теряется, и у отправителя сообщение останется в статусе SENT. READ-ACK не повторяется при сбое отправки после установки флага.
- **ID сообщения в конверте — обязательное добавление.** Добавлено поле `Message.remoteMessageId` и `messageId` в конверте, чтобы ACK был с чем сопоставлять.
- **Статусы движутся только вперёд.** `IncomingMessageProcessor.advanceStatus` игнорирует ACK, который откатил бы статус назад.
- **Flush очереди: ОДНО соединение и одно полное рукопожатие НА ОДНО сообщение.** Батч-пересылка НЕ реализована и не реализуется без предварительного персистентного `CounterStorage` (D-6).
- **Батч допустим только для READ-ACK.** При открытии чата уходит ОДИН ReadAck на все неподтверждённые входящие.
- **Идемпотентный приём.** Дубликат по `(contactId, remoteMessageId)` не создаёт вторую запись и не вызывает уведомление, но DELIVERED-ACK уходит повторно.
- **Формат ACK.** Только тег типа + ID(ы) сообщения отправителя. Ни временных меток, ни ID контактов, ни содержимого.
- **POST_NOTIFICATIONS.** Запрашивается автоматически ОДИН раз при первом показе списка контактов (API 33+).
- **Миграция БД v1→v2** — явная `Migration`, без destructive-фолбэка.
- **ЭТАП B.8 — тип foreground-сервиса: `specialUse`.** Без лимита по времени, требует разрешение и обоснование в манифесте.
- **WorkManager зафиксирован на 2.9.1**, так как начиная с 2.10.0 требуется compileSdk 35, а проект сидит на 34.
- **Вибрация по умолчанию** для канала сообщений.
- **Счётчик непрочитанных** — UX-добавление. Инкремент только на новое сообщение, сброс при открытии чата.
- **Поле ввода поверх навигационной панели** — исправлен баг (Scaffold.bottomBar не получает insets автоматически).
- **ActiveChatTracker** — счётчик не увеличивается, пока чат виден (ON_START/ON_STOP).

## ЭТАП 2.5 — защита от анализа трафика (статус: в работе)

### 2.5-1. Выравнивание размера тела (`crypto/padding/FramePadding`)
Перед шифрованием тело `AppMessage` оборачивается в `[флаги 1 Б][длина 4 Б][payload][нули]` и округляется до корзин 128 / 256 / 512 / 1024 / 2048 / 4096 байт, выше — кратно 4096. Выравнивание целиком внутри AEAD. Подключено в `SecureLanChannel`.

**Эффект:** DELIVERED-ACK, READ-ACK с несколькими ID и текст до ~86 байт дают одинаковую длину кадра данных (корзина 128: длина кадра 4 + 128 + 16 = 148 байт, без байта типа и 8-байтового счётчика).

**Риск/ограничение:** длина выровненного тела — всё ещё функция размера сообщения с точностью до корзины.

### 2.5-2. Разрыв совместимости формата провода
Изменения 2.5-1, D-4 и снятие сигнатур (Шаг 3, включая удаление 8-байтового счётчика) несовместимы со старыми версиями. Решение владельца: оба устройства обновляются одновременно, обратная совместимость не поддерживается. Пока версии разные, сообщения не теряются: приёмник отбрасывает незнакомый формат, а отправитель оставляет сообщение в Outbox.

### 2.5-3. Правки крипто-ядра по правилу 0.6 (`IkHandshake.kt`)
- `computeTranscript` стал `internal` (для тестов).
- `startInitiator` выполняет DH сразу (некорректный ключ вызывает исключение раньше).
- Low-order эфемерные точки дают `null`, а не исключение.

### 2.5-4. Что остаётся видимым наблюдателю LAN после этапа
- Факт соединения, IP-адреса, время (D-3: одно сообщение — одно соединение, ACK тоже).
- Структура рукопожатия: три кадра фиксированных размеров 80 / 112 / 80 байт без байта типа и длины (M1 и M3 неразличимы по размеру, роль определяется позицией в автомате).
- Кадр данных: открыто только поле длины (4 байта), значение строго из набора корзин + 16 (AEAD-тег). 8-байтовый счётчик удалён с провода и считается неявно равным 0 (закрытый остаточный признак Шага 3).
- Порт: фиксированный TCP-порт (48765).
- mDNS: тип сервиса `_ramka._tcp.` виден, но вещание и обнаружение можно полностью отключить тумблером в настройках (по умолчанию ВКЛ). При выключенном тумблере TCP-слушатель остаётся активным.
- Тайминги: джиттер 0,5–5 с для ACK и ±20% для backoff Outbox скрывают точные интервалы, но не сам факт обратного соединения после сообщения.
- Активный зонд: фиксированный порт, закрытие молчащего соединения ровно через 10 с и мгновенное закрытие на мусор остаются отличительными признаками.

### 2.5-5. Ещё не сделано (по согласованному порядку)
- Фиктивный трафик (cover traffic) — опционально, выключен по умолчанию, только если оценка эффекта оправдает цену.
