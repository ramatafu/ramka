# ramka — Stage 1 (локальный зашифрованный чат по LAN)

## О проекте

`ramka` — приватный P2P-мессенджер для Android. Идея: два человека в одной
локальной сети должны иметь возможность переписываться, не проходя ни через
какой сервер вообще, с шифрованием, которое проверяемо аутентифицирует
собеседника (а не просто "шифрует трафик до кого-то"). Единственный источник
истины по функциональности и ограничениям — `PROJECT_SPEC.md` в корне репозитория;
этот README описывает конкретно то, что реализовано на Stage 1, и как это
проверить руками.

Текущий статус: Stage 1 (локальный LAN-чат, без сервера, без очереди
недоставленных сообщений — это Stage 2). Список того, что уже сделано, что
упрощено и почему — см. разделы ниже и **`DEVIATIONS.md`**.

## Модель угроз (кратко)

Это не полный анализ (полный — задача отдельного security review, см. D-1 в
DEVIATIONS.md), а краткая ориентировка: от чего Stage 1 защищает и от чего — нет.

**Защищает от:**
- Прослушивания содержимого сообщений в локальной сети (сквозное шифрование Noise IK).
- Подмены собеседника (взаимная аутентификация по Ed25519, верификация отпечатков ключей).
- (Этап 2.5) Вывода о типе и размере сообщения по длине кадра: тело перед шифрованием
  выравнивается до корзин (128…4096 байт, выше — кратно 4096), поэтому ACK и короткий
  текст имеют одинаковый размер (148 байт для корзины 128, без байта типа и счётчика).
- (Этап 2.5) Идентификации устройства по статическому ключу в рукопожатии (M1/M2/M3 зашифрованы).
- (Этап 2.5) Распознавания типа кадра и длины по открытым байтам (сигнатуры сняты).

**Не защищает от:**
- Компрометации устройства (ключи хранятся в Android Keystore, но если устройство в руках злоумышленника — игра окончена).
- Атак на уровне операционной системы (keylogging, скриншоты).
- (Этап 2.5) Некоторых остаточных метаданных: структура «соединение на сообщение» из четырёх кадров (D-3), фиксированный TCP-порт, mDNS-сервис `_ramka._tcp.` (отключаемый), тайминги ACK и повторов Outbox (сглажены джиттером, но факт соединения виден). Что именно и по какому плану снимается — в DEVIATIONS.md.
- Компрометации долговременного ключа ответчика (позволяет расшифровать M1 в записанном трафике, см. D-4).

## Что реализовано (Stage 1 + Этап B + Этап 2.5)

- **Криптография:** Noise IK-рукопожатие (X25519 + ChaCha20-Poly1305 + Ed25519), реализованное вручную поверх Bouncy Castle (см. D-1).
- **Сеть:** LAN-обнаружение через NSD (mDNS) со случайным эфемерным именем сервиса, плюс ручной ввод по QR-коду. Защищённый TCP-канал с `soTimeout` (10 с на handshake, 30 с idle).
- **Доставка:** Outbox с экспоненциальным backoff (30 с … 1 ч, с джиттером ±20%) через WorkManager и Foreground Service (`specialUse`).
- **Статусы:** Разделение SENT (успешное рукопожатие) и DELIVERED/READ (по факту получения ACK).
- **Уведомления:** Системные уведомления с вибрацией, корректный счётчик непрочитанных (badge), скрытие содержимого на заблокированном экране.
- **Защита от анализа трафика (Этап 2.5):** FramePadding (выравнивание размеров), шифрование метаданных рукопожатия (D-4), снятие сигнатур с кадров (фиксированные размеры 80/112/80 для рукопожатия, корзина+16 для данных, без типа и счётчика), джиттер для ACK, тумблер mDNS в настройках.
- **TURN для звонков (Settings → «TURN-серверы»):** список пользовательских серверов с приоритетом, TCP fallback, пароли в `SecureKeyStore`, миграция из версии с одним сервером — см. раздел «TURN-серверы».
- **Диагностика сети (Settings → «Проверить скорость интернета»):** Ping/Jitter через relay, Download/Upload через пользовательский https-URL, цветовая оценка и рекомендации — см. раздел «Диагностика сети (Speedtest)».

## TURN-серверы

Звонки (WebRTC) идут напрямую между устройствами (P2P) и по локальной сети. Чтобы они работали и через
мобильный интернет или за строгим NAT, пользователь добавляет **свои** TURN-серверы. В приложении нет
ни одного встроенного TURN-сервера и ни одной встроенной учётной записи.

**Где:** Настройки → «TURN-серверы». Пошаговая инструкция по установке собственного Coturn есть в приложении
(экран `TurnGuideScreen`); в ней логин и пароль показаны заглушками `ВАШ_ЛОГИН` и `ВАШ_ПАРОЛЬ`.

- **Несколько серверов с приоритетом.** Список карточек: адрес (`turn:хост:порт` или `turns:хост:порт` для TLS),
  логин, переключатель «включён», кнопки «вверх»/«вниз» и «удалить» (с подтверждением). Чем выше сервер в
  списке, тем выше его приоритет при звонке. Нажатие на карточку открывает редактирование.
- **TCP fallback.** Для каждого включённого сервера `turn:` кроме основного адреса (UDP) добавляется резервный
  `…?transport=tcp` — для сетей, где UDP режется. Для `turns:` резервный адрес не добавляется: он и так работает по TCP/TLS.
- **STUN и пустой список.** Публичный STUN (`stun:stun.l.google.com:19302`) добавляется всегда. Если TURN-серверов
  нет (или все выключены), звонок работает только через STUN — то есть в локальной сети (Wi-Fi) и при прямом соединении.
- **Безопасное хранение паролей.** Пароль каждого сервера хранится только в `SecureKeyStore` (ключ
  `turn_password_<id>`). В DataStore лежит лишь список записей (адрес, логин, флаг, порядок) в виде JSON — без паролей.
- **Миграция со старой версии.** Если в прежней версии был настроен один сервер (адрес, логин и пароль), при первом
  обращении он переносится в список первой записью (включённость сохраняется), пароль перекладывается под новый
  ключ, старые данные удаляются. Неполные старые настройки не переносятся.
- Записи с неверным адресом, пустым логином или без пароля при звонке молча пропускаются.

## Диагностика сети (Speedtest)

**Где:** Настройки → «Проверить скорость интернета».

- **Ping и Jitter — через relay-серверы.** Тест делает 5 вызовов `RelayClient.check()` к первому рабочему relay
  из включённого пула (если первый не ответил как минимум на 3 из 5, берётся следующий). Ping — среднее время,
  Jitter — средняя разница между соседними замерами. Если пул релеёв выключен, к релеям тест не обращается.
  `check()` включает TCP, TLS и проверку токена, поэтому значения выше обычного ICMP-ping (примерно в три круга обмена).
- **Download/Upload — через ваш URL.** На экране есть поле «URL для теста скорости» (по умолчанию пустое).
  Нужен адрес вида `https://хост/путь` на файл примерно в 10 МБ на вашем сервере (только https). Download — GET
  этого адреса (не дольше 10 с и не больше 50 МБ). Upload — POST 1 МБ на тот же адрес; если сервер POST не принимает,
  Upload пропускается с пояснением. **Если поле пустое, измеряются и показываются только Ping и Jitter.**
- **Цветовая индикация** (цвет дублируется словом «хорошо / средне / плохо»):

  | Метрика | Зелёный | Жёлтый | Красный |
  |---|---|---|---|
  | Ping | < 50 мс | < 100 мс | ≥ 100 мс |
  | Jitter | < 20 мс | < 50 мс | ≥ 50 мс |
  | Download, Upload | ≥ 5 Мбит/с | ≥ 1 Мбит/с | < 1 Мбит/с |

- **Рекомендации.** Низкая скорость → «Рекомендуется использовать Wi-Fi или настроить TURN-сервер»; высокий
  Jitter → «Нестабильное соединение. Звонки могут прерываться»; высокий Ping → предупреждение о паузах в звонках;
  всё хорошо → «Скорость достаточна для звонков и передачи файлов» (если скорость не измерялась — подсказка указать URL).
- **Не чаще раза в час.** Результат кэшируется на час (ключ — URL и набор релеёв); в этот срок кнопка показывает
  сохранённый результат, а «Всё равно повторить» запускает новый тест.

## Безопасность

- **Никаких захардкоженных TURN-серверов, адресов и учётных данных.** Все TURN-серверы, их логины и пароли, а также
  URL для теста скорости вводит пользователь. Единственный зашитый адрес — публичный STUN `stun.l.google.com:19302`
  (по заданию); при звонке он видит публичный IP устройства (см. DEVIATIONS.md, T-3).
- **Пароли и токены — только в хранилище на базе Android Keystore.** Пароли TURN и токены relay лежат в `SecureKeyStore`;
  в DataStore, Room, JSON и в `toString()` моделей их нет (`TurnCredentials` печатает `password=***`).
- **Логи без секретов.** Код TURN и Speedtest пишет в лог только тип исключения и счётчики — без паролей, логинов,
  токенов и адресов серверов. Ограничение: отладочный лог ICE-кандидатов в `CallViewModel` выводит их целиком, а это
  IP-адреса (локальные, публичные, адрес TURN); пока он не вычищен.
- **Speedtest только по https.** Открытый HTTP в приложении запрещён манифестом; адрес с логином и паролем внутри
  (`https://user:pass@…`) не принимается.

## Архитектура проекта

ramka/
├── app/        — UI (Jetpack Compose), ViewModels, Hilt DI, настройки (в т.ч. TURN-серверы, Speedtest), уведомления
├── domain/     — бизнес-логика, use cases, модели (AppMessage, Contact, Message), репозитории (интерфейсы)

├── network/    — LAN-обнаружение (NSD), защищённый TCP-канал (рукопожатие + доставка)
├── crypto/     — Noise IK (IkHandshake), SessionCipher, KeyManager, SecureKeyStore, FramePadding
└── storage/    — Room DAO, миграции БД


## Как проверить вручную

1. **Установка:** Соберите и установите APK на два устройства в одной Wi-Fi сети.
2. **Сопряжение:** На устройстве A нажмите «+», отсканируйте QR-код с устройства B. Проверьте отпечатки ключей.
3. **Отправка:** Напишите сообщение на A. На B оно должно появиться мгновенно.
4. **Статусы:** На A значок у сообщения должен стать ✓ (пришёл DELIVERED-ACK).
5. **Прочтение:** Откройте чат на B — у A значки меняются на ✓✓ (один READ-ACK на все неподтверждённые).
6. **Офлайн-доставка:** Выключите Wi-Fi на B, отправьте сообщение с A. Включите Wi-Fi на B — сообщение доставится, статус обновится.
7. **Backoff:** С выключенным Wi-Fi на B наблюдать (в отладочной сборке) паузы между попытками отправки (30 с, 1 мин, 2 мин... с джиттером).
8. **Уведомления:** Сверните приложение на B, отправьте сообщение с A. Должно прийти уведомление «ramka — Новое сообщение» с вибрацией.
9. **Настройки:** Зайдите в настройки на B, выключите «Автообнаружение в сети (mDNS)». С устройства A (или ноутбука) сервис `_ramka._tcp.` должен перестать обнаруживаться, но отправка по старому QR-адресу (если он сохранён) или ручному вводу IP:порт должна продолжать работать.
10. **TURN-серверы:** Настройки → «TURN-серверы». Пустой список показывает подсказку. Добавьте сервер (`turn:хост:порт`, логин, пароль), второй сервер, поменяйте порядок стрелками, выключите переключателем, удалите. Совершите звонок по мобильному интернету: в отладочном логе (`ramka`) будет «ICE: STUN + TURN-серверов: N».
11. **Speedtest:** Настройки → «Проверить скорость интернета». С пустым полем URL нажмите «Начать тест»: появятся только Ping и Jitter. Укажите `https://…` на файл ~10 МБ — добавятся Download и Upload. Повторный запуск в течение часа покажет сохранённый результат.

## Известные ограничения и отклонения

Полный список и обоснования — в **`DEVIATIONS.md`**. Кратко:
- Рукопожатие реализовано вручную, а не через noise-java (D-1).
- Нет Double Ratchet, ключи сессии статичны в рамках одного соединения (D-2).
- Одно сообщение = одно TCP-соединение с полным рукопожатием (D-3).
- Этап 2.5 в основном завершён: реализованы фиксированные кадры рукопожатия (80/112/80) и данных (корзина+16) без типа и счётчика, джиттер ACK/Outbox, soTimeout на входящих соединениях, тумблер mDNS. Остался опциональный фиктивный трафик (DEVIATIONS.md, 2.5-5).
- Мульти-TURN и Speedtest: JSON на `org.json`, Speedtest по пользовательскому https-URL, Ping через `RelayClient.check()` (выше ICMP), публичный STUN зашит (DEVIATIONS.md, раздел «Мульти-TURN и диагностика сети»).

## Сборка и разработка

- **Минимальная версия Android:** API 26 (Android 8.0)
- **Целевая версия:** API 34 (Android 14)
- **Язык:** Kotlin 1.9+
- **Сборка:** `./gradlew assembleDebug`

**Известные warnings при сборке:**
1. Неиспользуемый импорт `X25519PublicKeyParameters` в `KeyManager.kt` (можно удалить).
2. `Deprecated in Java` для методов `NsdManager.resolveService` и `serviceInfo.host` (Google планирует обновить NSD API, но текущий код работает стабильно на API 34).
3. `Parameter 'contactId' is never used` и `'Send: ImageVector' is deprecated` в `ChatScreen.kt` (косметические замечания Compose).
4. `@file:Suppress("DEPRECATION")` в `SecureKeyStore.kt` (библиотека `androidx.security:security-crypto` помечена как deprecated с версии 1.1.0, официальной замены пока нет).
